# skill 让整张图归位

"会用工具的动物"这个定义，缺口不在能力，在身份。它说清了 agent 能做什么：调工具、跑循环、把活干完。却说不清这个 agent 是谁。同一段循环，换一个目的就是另一个 agent，而定义里没有放"目的"的地方。

skill 出现的时候，缺口补上了一角，也让那套散着的零件开始归位。

## 从 skill 这一点开始

skill 容易被看成又一个工具。但它和工具不是一类东西。工具是一次调用，用完即弃，下一轮对话不会跟着 agent 走。skill 有名字，可以复用，可以从一个 agent 挂到另一个 agent 上，效果不会差太远。一个可命名、可复用、可迁移的能力单元，这正是技能长在一个人身上的样子。会做 PPT 的人，换一家公司也会做 PPT。

到这里冒出一个念头：skill 像简历上的一条。

这个念头不解决任何工程问题，它只是一点火光。但就是这点微光，照见了一个更大的联想：如果 agent 身上的能力可以按简历条目来理解，那 agent 这个整体，也许也该按一个人来理解，而不是按一个会调工具的程序来理解。

换个抽象看同一个东西，多数时候什么也看不出。这一次不一样，借着这点光，整张图忽然归了位。

## 顺着这条线，零件一个个对上

把 agent 当一个人来看，原先各自孤立的零件开始自动落位。

系统提示词落位成 JD。它写的本就是这个岗位干什么、汇报给谁、什么能碰什么不能碰。它是一份岗位职责说明，不是一段需要反复调试的咒语。

模型分级落位成资历。Opus、Sonnet、Haiku 的差别，对应资深、中级、初级的能力与价码。派活要看资历：让最贵的人去做每天一次的格式转换是浪费，让最便宜的人去扛长链推理是冒险。

长期记忆是职业履历。做过什么、踩过什么坑、某个客户的偏好是什么，都记在案，换一份工作还能带走。

带持久化卷的沙箱是工作电脑。文件、依赖、配置、半成品工程都在这台机器上，今天调好的环境明天还在，今天的活可以接着明天干。

零件对上标签，还算不上什么，比喻谁都能凑。让这套看法立住的，是零件之间的关系也跟着对上了。JD 约束这个人该用哪些 skill，而不是把简历上的所有本事都使出来。资历决定该把哪一档的活派给他。履历跟着人走，换岗不丢。这些关系不是事后硬安进去的。把"一个人"这个抽象套上去，它们自己就浮出来了。

## 这不是比喻，是抽象

一个看法能不能被当真，有一条朴素的判据：它能不能把已经摆在那里的东西，不牵强地解释一遍。

人力资源这套看法过了这一关。agent 当时已经有的零件，系统提示词、skill、模型分级、长期记忆、持久化沙箱，没有一个需要削足适履，全都落进了位置，连它们彼此之间的关系都对得上。能做到这一步的，就不再只是帮助理解的比喻，而是一个稳定的抽象。

比喻可以拿掉，话照样说得通；抽象拿掉了，整套说法就散了。人力资源在这里属于后者。用它去看 agent，"prompt 写得好不好"变成"JD 写得清不清楚"，"该用哪个模型"变成"这个岗位配多高的资历"。问题被重新组织了一遍。

到这里，图归位了。
