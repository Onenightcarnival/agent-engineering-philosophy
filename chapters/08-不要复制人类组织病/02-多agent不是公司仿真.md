# 多 agent 不是公司仿真

把 agent 当打工人看，不必把一群 agent 摆成一家公司。

人力资源视角好用，是因为它让岗位、能力、履历、环境、责任这些工程对象重新排好位置。它不是让工程师照着公司组织结构，给 agent 起一堆职级和部门名。

公司是人类组织在特定成本、法律和人性条件下长出来的形态。agent 团队面对的是另一组条件。工作可以瞬时 fan-out，角色可以临时生成，trace 可以完整留下，记忆可以复制或销毁，权限可以精确收回。既然底层条件变了，就不该把公司当模板整套搬来。

## 仿真会带来多余结构

公司仿真最常见的样子，是给 agent 团队安上人类组织的外壳：经理、主管、员工、会议、汇报、审批、日报。看起来完整，实际只复制了形式。

人类组织需要很多仪式，是因为人会遗忘、会隐瞒、会争功、会回避责任，也因为信息在组织里传得慢、失真多。agent 团队未必需要同样的外壳。一个 trace 已经记录清楚的过程，不一定还要写一份向上表演的周报；一个权限系统已经禁止的动作，不一定还要层层口头审批；一个临时子任务完成后即销毁的角色，不一定需要一套长期职级。

仿真会让多 agent 系统背上不必要的管理负担。更糟的是，它会把人类组织里的失败规律也带进来：让层级替代事实，让汇报替代工作记录，让流程感替代责任。

## 岗位也要接受审计

把 agent 当打工人看，不等于岗位越多越好。

岗位是工程对象，不是组织装饰。它应该写清职责、权限、交付物和升级条件。但岗位切得过细，也会制造复杂度。一个通才 agent 本来可以在同一工作面里完成的任务，被拆成三个岗位以后，就多了三份交接物、三段上下文压缩、三处责任边界。拆分没有带来更好的判断，只带来了更多接口。

所以每个岗位都要被问一遍：它是任务结构需要的，还是人类组织惯性留下的？它增加了事实独立性，还是只增加了流程感？它降低了风险，还是把一个清楚的问题拆成几个模糊的交接？

虚假岗位要删除，真实边界要保留。

## 设计要从约束出发

多 agent 团队应该从约束出发，不从公司形状出发。

如果问题是分工，就设计岗位边界；如果问题是交接，就设计交接物和验收标准；如果问题是风险，就设计授权和升级路径；如果问题是质量，就设计 eval 和工作记录；如果问题是责任，就设计最终收束点。

这些东西在人类组织里也有，但它们靠协作本身成立，不靠公司这个外壳成立。公司只是历史上承载这些约束的一种形态。agent 团队可以借它的经验，不必复制它的外壳。
