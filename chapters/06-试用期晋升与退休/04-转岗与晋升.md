# 转岗与晋升

agent 也会换岗，也会被委以更重的职责。这时候要问：什么能跟着走，什么不能？

## 有些东西可迁移，有些不能照搬

职业证书级的 skill 可以迁移，履历可以参考——这两样跨岗位仍有价值。一个会做代码审查的 skill，换个项目还能用；一段"这类任务上踩过什么坑"的履历，换个岗位也有借鉴。

但岗位经验不能照搬。一个客服岗 agent 攒下的客户脾性、内部工单系统经验，换到风控岗，大部分作废。那些经验是为旧岗位长出来的，绑在旧岗位的上下文里。这正对应第四章那条线：上岗培训是岗位特定的，职业证书才是可迁移的——转岗时，前者大半要重来，后者能带走。

## 晋升不是把旧 agent 原样推上去

晋升也一样。给一个 agent 更重的职责，不是把原来那个原样推上去。

它是一次重新组合：重写 JD（职责变了），可能换一档更高的模型（学历要匹配新职责），保留可迁移的部分（证书 skill、履历），重建岗位特定的部分（新的上岗培训、新的工作环境）。把晋升想成"同一个 agent 变强了"，会漏掉重写岗位这一步，结果是一个揣着旧 JD 干新活的 agent——又回到第三章那个岗位错配的老问题。

所以转岗和晋升都要按新岗位重新组合：迁移能迁移的，重建岗位特定的。能不能搬，取决于那样东西当初是为岗位长的，还是为这个角色本身长的。

## 同一个 agent，看的是记录是否连续

到这里会冒出一个疑问：JD 重写了，模型换了，环境重建了，凭什么说这还是"同一个"agent？

这个问题不必交给哲学。哲学争了两千年也没争出结论——今天的你和十年前的你，细胞换过了，性格变了，技能也不是原来那套。但公司从不为此困扰。人事制度看的不是哲学上的同一性，而是工号、合同和档案有没有延续：工号不变，合同主体不变，档案连续，他就是同一个员工。工程上判断是不是同一个 agent，也看这条记录有没有断，不是追问它有没有同一个"灵魂"。

agent 照此办理。模型可以换，JD 可以重写，环境可以重建，只要履历这条线不断、绩效和责任记在同一个名下，它就还是它。零件可以换，记录要连续。

于是"晋升不是把旧 agent 原样推上去"和"晋升之后它还是同一个 agent"，两句话不矛盾：前一句说的是零件，后一句说的是记录。
