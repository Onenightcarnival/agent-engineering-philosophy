# 上下文隔离与共享

多 agent 系统最容易被误解的一点，是以为 agent 越多，知道得越多越好。于是所有 agent 共享同一份上下文，读同一堆材料，看同一段历史，最后给出一组看似独立、实际同源的判断。

这不是团队协作，只是一群角色挤在同一个脑子里说话。

## 隔离是为了保留差异

分出多个 agent，第一件事是隔离。

批判 agent 不该先读主写 agent 的自我辩护，否则它会沿着对方的路继续走。事实校验 agent 不该先接受结论，否则它会替结论找证据。风格 agent 不该替结构 agent 决定论点，否则语气会抢走判断。

上下文隔离保留的是判断差异。不同岗位看到不同材料，带着不同标准进入同一件事，才可能互相纠偏。所有人从同一个上下文出发，再换几个角色名，通常只是同一种偏差的多次复述。

所以多 agent 的第一条设计原则是：不要默认共享全部上下文。先问这个岗位需要知道什么，又不该被什么提前影响。

## 共享是为了完成交接

但隔离不能走到另一个极端。完全隔离的 agent 只是几个人各写一份答案，不是团队。

共享发生在交接点上。上游交给下游的，不该是自己的全部思考过程，而是下游需要的交接物：结论、依据、未决问题、风险标记、不能碰的边界。传少了，下游缺判断依据；传多了，下游被噪声淹没，也更容易继承上游的偏见。

这和第五章讲记忆是同一条原则：传递提炼过的必要上下文，不传原始流水。多 agent 团队的上下文设计，就是决定哪些东西要隔离，哪些东西要在交接时压缩后共享。

## 共享真相，隔离判断

一个好用的切法是：共享真相，隔离判断。

事实材料、约束条件、最终交付标准，应该尽量共享。它们是团队对齐的地面。判断过程、假设路径、初稿偏好，要按岗位隔离。差异从这里长出来。

如果所有 agent 都共享同一套判断，它们不会形成团队，只会形成回声。多 agent 的价值，不在人数，而在被设计出来的差异。下一篇用写作这个场景，把这件事说透。
