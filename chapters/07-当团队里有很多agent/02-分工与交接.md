# 分工与交接

多个 agent 协作，要紧的不是"一起跑"，是交接。一个 agent 的产出成为另一个的输入，协作的质量就压在这个交接点上。

人类团队里出岔子，常常不在某个人身上，在两个人之间——信息漏在中间，责任卡在缝里。agent 团队会犯同样的错，而且更隐蔽，因为 agent 默认不会主动追问澄清（除非你把它设计成会）。交出去的东西含糊一点，接手方不会皱眉发问，它会照着含糊的输入往下做，把错误一路传下去。

## 交接点上的三样东西

一个交接点靠不可靠，取决于三样东西。

交付件：交出去的到底是什么。格式、完整度、约定，都要明确。这正是第四章"可复现"在协作里的延伸——一个交付件要像证书级 skill 那样自足，接手方不用靠猜补齐缺的前提。

责任边界：到哪是上游的、从哪是下游的。中间不能留模糊地带。一旦有一段"谁都觉得对方会管"的灰色区域，出了事就卡在那里无人认领。

上下文传递：接手方需要知道的背景，怎么不丢、也不过载地传过去。传太少，下游缺判断依据；一股脑全传，又把对方淹没。传递的是提炼过的必要上下文，不是原始流水——这和第五章对记忆的要求是同一个道理。

## 问题常出在交接处

把这三样当成一等公民来设计，团队才稳。

常见的误区是把力气全花在打磨单个 agent 上，默认它们接起来自然就能配合。但协作最容易出问题的地方，不是单个 agent，而是两个 agent 之间的交接。两个都很强的 agent，交接含糊，照样协作失败；两个能力一般的 agent，交付件清楚、责任边界分明、上下文传递干净，反而配合得很好。设计团队，先盯交接。
