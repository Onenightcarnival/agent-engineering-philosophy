# 岗位错配比能力不足更常见

agent 跑不好，第一反应几乎都是同一句：模型不行，换个更强的。

这句话偶尔对，多数时候不对。更常见的真因不是能力不足，是岗位错配——JD 没写清、职责打架、用人方式不对。换模型治的是标，重新定义岗位治的是本。

## 错配的几种典型

岗位错配有几副固定的面孔。

一种是岗位太宽。一个 agent 既做规划、又做执行、又做审查，三个本该分开的职责挤在一份 JD 里，于是它一边干一边自我怀疑，规划被执行打断，审查又对自己手软。这不是模型不够聪明，是一个人被塞了三个互相打架的岗位。

一种是用人方式与岗位不符。JD 把它定义成一个窄岗，调用时却当全才使唤，什么都丢给它；或者反过来，明明需要它连续负责一摊事，却每次都当一次性工具来调，不给它记忆和环境。

还有一种是边界缺失，就是上一篇说的——越权或不作为，都从这里来。

这些毛病的共同点是：症状出在 agent 的行为上，病根在岗位的定义上。盯着行为去调模型，是在治标。

## 先调 JD，再调模型

于是有一条操作上的次序：调试 agent，先调 JD，再调模型。

行为不对，先回去看岗位——职责是不是太宽、边界是不是没划、用人方式是不是和定义不符。把这些理顺，很多"模型不行"的问题会自己消失。确实理顺了岗位、行为还是上不去，才轮到怀疑资历不够，去换更强的候选人。

这一章到此收口，正好和上一章夹出同一个词。上一章说学历不是岗位胜任，这一章说错配比能力不足更常见——两边都指向"匹配"：先有清楚的岗位，再谈合适的人。把岗位定义当成 agent 工程的主战场，而不是把模型选型当成主战场，是这本书的一个基本立场。
