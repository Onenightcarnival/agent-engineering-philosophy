# 不是又一本 agent 框架指南

## 引言

agent 这个领域正在被"怎么做"淹没。框架文档、编排教程、multi-agent 速查表、prompt 模板合集、"年度最值得关注的 N 个 agent 框架"——它们有一个共同的默认：读者只想知道一件事，告诉我怎么搭。怎么挂工具、怎么串 multi-agent、怎么写 ReAct 循环、怎么接 MCP。这些问题值得回答，但它们背后有同一个盲区：没人停下来问，当 agent 成为软件的基本构件，工程本身需要做出什么调整。

这本书关注的是"怎么想"，然后才是"怎么做"。

有件事得先交代，因为它可能影响你怎么读：我自己正在做一个 agent 框架。但这本书不是它的说明书，更不是它的软文。恰恰相反——正因为在框架里趟过，我更清楚框架能解决什么、解决不了什么。框架统一的是表面的流程；真正难的那层——这个 agent 是谁、配多高的资历、能力怎么迁移、责任落在谁头上——没有哪个框架替你回答得了。这本书写的就是那一层。

## 这本书在做什么

一个人对"当 agent 成为软件的基本构件，工程该怎么做"这个问题的系统性回答。"一个人"意味着它表达的是个人观点，有明确的偏好、明确的判断、明确的品味。背后的偏见和盲区，在个人立场里显式标注，供你校准。

具体而言，这本书做三件事：

立一个稳定的抽象。 agent 到底是什么？这本书的答案是：把它当一个人看——一个有岗位、有技能、有履历、有工作环境的同事。这不是煽情的比喻，是一套能承重的工程视角。第一章专门论证它凭什么不只是比喻。

顺着这套抽象走一遍 agent 的一生。 出生（训练）、入职（选型与 JD）、上岗（skill）、安家（沙箱与记忆）、试用与晋升（eval 与成长）、组成团队（多 agent 协作）。每一章拿"把 agent 当人看"去解一个具体的工程问题。

落到工程启示。 隐喻要落到具体的工程判断上才算数：prompt 写得好不好，重述成 JD 写得清不清楚；该用哪个模型，重述成这个岗位配多高的资历。问题被重新组织一遍，原先散落的决策才接得上。停在比喻趣味上的隐喻，这本书会把它拆掉。

这本书的起点是：假设你已经知道怎么把一个 agent 跑起来，现在的问题是怎么把它当成一个可靠的、能共事的角色来工程化。所以某个 SDK 的 API 怎么调、某个框架的工作流怎么配、ReAct 和 Plan-and-Execute 的循环细节，这些有专门的文档讲，这里不重复。

## 为什么是现在

agent 的定义这两年换得太快，快到行业还来不及在正确的层级上理解它。一会儿它是"会调工具的程序"，一会儿又被吹成"无所不能的智能体"。两个说法都停在能力上，都没说清 agent 是谁。

而该凑齐的零件其实已经凑齐了：skill 让能力可以挂载和迁移，持久化沙箱给了它一台自己的电脑，长期记忆让它攒得下履历，模型分级给了它资历的刻度。零件都在，缺的是一个把它们串起来的抽象。没有这个抽象，框架只能统一表面的流程，零件只能各管各的堆在一起。现在正是补这个抽象的时候。

## 全书结构

第一章立抽象：agent 到底是什么，为什么"把它当人看"是一个能承重的抽象，而不是顺手的比喻。第二章到第六章顺着这套抽象走完 agent 的个体一生——出生以前的训练、岗位先于候选人、上岗培训与职业证书、工作电脑与职业履历、试用晋升与退休。第七、第八章从个体走到团队与组织：一群 agent 怎么协作，以及当传统组织变成 agentic 组织，什么会变、什么不会变。

起点是一个判断（agent 是比模型高一层的抽象），终点也是一个判断（agentic 组织里，什么必须由人守住）。

## 阅读建议

如果你在搭 agent 系统时撞上了"prompt 调不稳""不知道该信哪个 eval""multi-agent 越编排越乱"这类问题，可以直接跳到对应章节，但建议回头补读第一、二章——很多问题的根不在框架层，在你还没想清这个 agent 到底是谁。

如果你对框架和工具本身更感兴趣，这本书可能让你不舒服。它会反复追问"为什么"，而不是直接给你"怎么做"。这是刻意的选择：框架会过时，抽象不会。今天的 SDK 三年后可能没人用，但"先定义岗位，再挑候选人"这件事，只要 agent 还像个打工人，就一直成立。

你不同意书里的判断，再正常不过。如果你在每个问题上都点头，这本书对你的价值反而有限——它没给你带来新的视角。有价值的读法是：有些地方深有同感，有些地方想立刻反驳，而反驳的过程，逼着你把自己的立场讲清楚。
