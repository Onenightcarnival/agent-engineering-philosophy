# 序章：为什么写第二本书

第一本书《大模型应用工程哲学》写的是：当软件系统的核心组件从确定性函数变成概率性语言模型，软件工程需要做出什么调整。那本书的原始单元是模型——一个会出错的概率组件。你工程化的对象，是建在它之上的应用。

这本书换了一个原始单元。

## 抽象升了一层

agent 这两年的定义换得很快。最早讲 agent，接近"会用工具的动物"：一个模型，能调几个 function，能跑个 loop，就叫 agent。这个定义不算错，但太单薄——它只描述了 agent 能做事，没描述 agent 是谁。

当 skill、持久化沙箱、长期记忆、模型分级这些东西凑齐之后，一个更稳定的抽象浮现出来：agent 不像一只会拿工具的动物，而像一个完整的打工人。

- 系统提示词，其实是 JD：写清楚这个岗位干什么、汇报给谁、什么该做、什么不该碰。
- skill，是简历上的技能条目；要跨 agent、跨环境复用，就得像证书一样可验证。
- 基础模型，像候选人的资历：Opus 是资深专家，Haiku 是初级员工，岗位和能力要匹配。
- 长期记忆，是职业履历：做过什么、踩过什么坑、客户偏好是什么，跳槽也能带走。
- 带持久化卷的沙箱，是打工人的电脑：文件、缓存、配置、半成品工程，都在这台机器上。

这套抽象比"会用工具的模型"更完整。它关心的不只是 agent 能做什么，还包括它在哪个岗位上，带着什么技能和履历干活。工程化的对象，从"用模型搭的应用"变成了"agent 这个角色"本身——这是比模型高一层的抽象，不是同一层的更深一刀。

## 这本书不重讲第一本

第二本会反复擦到第一本的地盘：不确定性、声明式提示、类型契约、skill 的可移植性。边界要钉死——凡是能在模型层讲清的，引用第一本，不在这里重讲。这本书从"agent 作为自主角色"起步，往上写到团队与组织。

一句话区分两本书：第一本是怎么和一个不靠谱的函数相处，这一本是怎么和一个不靠谱的同事相处。

## 不是又一本 agent 框架指南

和第一本一样，这本书关注的是"怎么想"，然后才是"怎么做"。不是 agent 框架的使用手册，不是 multi-agent 编排的速查表，不是某个 SDK 的教程。是一个人对"当 agent 成为软件的基本构件，工程该怎么做"的系统性回答。有明确的偏好、明确的判断、明确的品味。
